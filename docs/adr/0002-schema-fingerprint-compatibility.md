# ADR 0002: Preserve legacy fingerprints while specifying a stable successor

Status: legacy compatibility decision accepted for v0.3.1; successor format proposed.

## Evidence

The identical `Stock` model in `tests/fingerprint_models.py` was run under
Pydantic 2.12.0 and the locked 2.14.3 on Python 3.12. The committed snapshots have
different SHA-256 fingerprints. Decimal fields in 2.12 contain generated string
patterns that 2.14 omits. YHMF's comparison reports validation changes even though
the persistence types, layout, keys, constraints, and ownership are unchanged.
Pydantic documents the removal in its
[2.14 release notes](https://pydantic.dev/articles/pydantic-v2-14-release).
This proves a concrete compatibility risk within the declared dependency range;
it does not establish every difference between those runtime versions.

## Decision for v0.3.1

Do not replace identity generation in a patch release. Keep existing snapshot
bytes and record fingerprints unchanged. Reject a mismatching runtime declaration
rather than guessing semantic equivalence, rewriting metadata automatically, or
silently accepting a model that may validate differently. Keep the Pydantic
version pinned in each application's lockfile for the lifetime of an installed
schema. An application upgrading from v0.3 with that same runtime remains
compatible. Upgrading Pydantic is a separate schema-compatibility event.

Fixtures establish exact legacy generation under both tested versions and verify
that foreign metadata remains inspectable and is never overwritten. CI runs the
fingerprint regressions against both versions. No claim of cross-version
fingerprint stability is made for legacy format one. Applications must not delete
installed metadata to bypass a mismatch or use adoption to bless it.

## Proposed framework-owned representation

A successor snapshot uses `format_version: 2`, separately from `layout: 1`.
The document contains `global`, `version`, `key`, and a recursively described
`fields` array sorted by storage field name. Each field contains its storage name,
kind (`scalar`, `embedded`, `children`, `reference`), nullability, required state,
index/unique flags, and an explicit scalar codec identifier where applicable.
Owned fields contain child key identity and node schema version; references
contain target global, key name/type, and deletion policy. Literal defaults use
framework-tagged scalar values, not a dependency's JSON serialization. Factories
are described as factories and never executed during schema generation.

Supported constraints are extracted from field metadata into framework-owned
names and tagged values: bounds, lengths, decimal precision, patterns, and strict
value policy. Unknown constraints fail representation generation until supported;
they must never be silently dropped. Arbitrary validators cannot be fingerprinted
reliably from Python function identity. Their compatibility contract remains the
explicit root/owned schema version, with documented responsibility to increment
it when validation behavior changes. Presentation titles, descriptions, `$defs`
names, and generated Decimal lexical patterns do not participate.

Serialize compact sorted-key ASCII JSON with finite numbers only, and hash those
canonical bytes using SHA-256. Versioned parsers convert each supported snapshot
format to a shared persistence descriptor for comparisons. Unknown format
versions fail safely. Format version changes require explicit migration.

## Compatibility strategy before activation

Implement and test legacy-to-descriptor conversion before emitting format two.
Keep reading format-one databases under their exact legacy identities. A reviewed
metadata migration must bind both saved source bytes and the new descriptor,
validate all persisted values and relationships, and reuse the maintenance gate,
fingerprint barrier, bounded record retagging, durable resume, and atomic
activation. Old clients must reject the barrier and, after activation, the new
identity. New clients must not treat a v1/v2 comparison as permission to write.

Test databases generated by both qualified legacy runtimes, mixed-client rejection,
interruption and abort, and unchanged field/index bytes. Only after these pass
should new databases default to format two. This patch introduces neither a new
on-disk format nor a metadata migration. Runtime migration to format two remains
future work; the design must not be mistaken for an implemented feature.

## Tradeoffs

Normalizing a few generated JSON Schema details in place would conceal additional
future drift and alter existing identities. Pinning an exact Pydantic dependency
for the library would force one runtime onto all applications and could itself
break existing installs created by another compatible version. Application-level
pinning preserves current installations while fixtures expose the known risk.
