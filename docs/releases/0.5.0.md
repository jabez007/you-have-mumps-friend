# v0.5.0: Schema stability, reliability, and developer experience

v0.5 establishes a framework-owned persistence contract, adds adversarial
correctness evidence, and exercises the public API in a warehouse inventory ledger.
The three phases were implemented and qualified sequentially, with logical commits
pushed after each slice. GPL-3.0-or-later and the `mccann_hub.yhmf` namespace remain.
No runtime or development dependency was added.

## Architecture and compatibility

Canonical schema format 2 is generated from compiled registry semantics, field
constraints/defaults, codecs, ownership, references, indexes, and application
revisions. It is independent of Pydantic JSON Schema output. Format, application
revision, storage layout, and codec versions are distinct. Golden fixtures match
under both qualified Pydantic versions. Class names, presentation, field order,
false mapper flags, and explicitly spelling the default reference policy do not
create persistent identity changes.

Existing v0.3/v0.4 format-one metadata and record fingerprints remain unchanged.
Transactions read both live metadata nodes and bind verified legacy declarations
to their installed identity. Pure bounded parsing/compatibility caches cannot hide
changed stored bytes. Opening or writing a compatible database does not convert
metadata or retag records. Actual migrations use the existing gate/checkpoints and
can activate a canonical target; old jobs resume their exact saved manifests.
New format-two databases require v0.5 clients.

Applications must advance the owning `__schema_version__` for persistence-relevant
custom validator, factory, or model-hook changes. Function bodies and historical
rules omitted by legacy snapshots cannot be reconstructed automatically. See
[the compatibility contract](../schema-compatibility.md) and
[ADR 0006](../adr/0006-canonical-schema-contracts.md).

## Findings and fixes

- Legacy Decimal fingerprints demonstrably differed between Pydantic 2.12.0 and
  2.14.3. The committed legacy fixtures still reproduce that difference; canonical
  fingerprints are stable across the qualified matrix.
- Final review found two equivalent-declaration cases that still differed because
  the initial producer copied incidental Field markers. Both minimal regressions
  failed before mapper metadata was compiled from actual registry semantics.
- Unpaired Unicode surrogates escaped through key/scalar codecs as Python encoding
  errors. Both regressions failed before the shared encoder began raising value-free
  `StorageError` exceptions.
- The realistic product query exposed an unhelpful missing-index error. A regression
  failed against the old message; errors now list usable primary/indexed paths while
  excluding predicate values and retaining explicit scan behavior.
- Generated mutation sequences found no additional mutation-integrity defect in
  the exercised workloads. This is evidence for those workloads, not a proof of all
  possible operation sequences.

## Public interfaces and application findings

CRUD and mutation signatures are preserved. `SchemaSnapshot.format_version` exposes
the representation version; inspection's `matching` status includes verified legacy
compatibility even when declared and installed fingerprints differ.

The [inventory application](../../examples/inventory/README.md) provides receive,
move, justified adjustment, stock lookup, and lot history through public YHMF APIs.
Products and lots have independent identities; warehouses own locations, bins, and
balances. Transactions maintain both sides of moves and independent ledger entries.
Duplicate movement IDs abort the command. Explicit Decimal arithmetic preserves
stock under a caller's low-precision context. Native tests cover competing moves
and a forced restart with one stable movement identity.

The local BinAddress value object removes repeated path construction. Strict mypy
now checks the example and library with explicit namespace bases. Remaining concrete
usability limits are casts for owned reads, root materialization in indexed stock
queries, and root-based rather than occurrence-based pagination. The general
persistence API does not impose ledger permissions; the example service is its
business-rule write boundary.

## Performance and remaining priorities

[Native inventory measurements](../inventory-performance.md) include environment,
raw samples, workload, median/p95/p99, adapter calls, and limitations. At 250 lots
per bin, the qualified transfer medians were 1.27–1.44 ms with partial mutations
versus 132–135 ms with grouped whole replacement. Partial transfer work remained
133 gets and 32 sets across 1/50/250 lots per bin. The 5.56–5.82 microsecond direct
assignment is a quantity-only lower bound without ledger or integrity work.
These warm serial results do not qualify production durability or throughput.

Recommended v0.6 priorities follow the observed constraints:

1. Bounded owned-occurrence query projection and pagination, so indexed inventory
   lookup can avoid materializing unrelated warehouse balances.
2. Typed owned-path reads that reduce casts without introducing automatic tracking
   or a general query language.
3. Measure real ledger contention on shared reference targets and cold child-insert
   capacity checks before choosing optimizations or new metadata.
4. Evaluate optimistic record revisions for detached workflows with an explicit
   layout/migration policy. Ordinary save remains last-writer-wins.

Broader/destructive migrations, automatic tracking, date/time codecs, and compound
keys remain outside this release. No general ORM expansion was introduced.
